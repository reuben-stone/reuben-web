Failure recovery & idempotency

Designing AI systems that fail gracefully - bounded retries, idempotent operations, crash recovery, and turning individual failures into durable system improvements.

01

Failure is normal in AI systems

AI systems fail differently from traditional software. The model might produce wrong output, hallucinate, loop, take too long, or make confident but incorrect claims. These are not edge cases - they are expected operating conditions.

The question isn't "will it fail" but "what happens when it fails." Good failure recovery limits blast radius, preserves progress, and creates learning opportunities.

Core principle: every failure mode has an architectural response - bounded retries for loops, idempotency for duplicate operations, independent verification for false claims, approval gates for consequential actions.

Concrete Artemis connection

  • Bounded retries prevent infinite loops when the model gets stuck
  • Idempotency keys prevent duplicate side effects on retry
  • Independent verification catches confident but incorrect claims
  • Approval gates pause the workflow before consequential actions
02

Idempotency

An idempotent operation produces the same result whether executed once or multiple times. This is critical for AI systems because retries are common - model timeouts, partial failures, crash recovery all trigger re-execution.

Implementation: key each consequential operation uniquely, check before executing, skip if already completed. The key must identify the specific operation in the specific workflow context, not just the operation type.

workflowId:stepId:toolName

This composite key uniquely identifies each consequential tool call. On retry, the system checks whether the key has already completed and skips if so.

Concrete Artemis connection

  • workflowId:stepId:toolName keys uniquely identify each consequential tool call
  • On retry, the system checks whether the key has already completed
  • This is enforced in code and tested with ordinary unit tests, not evals
  • The idempotency boundary protects against duplicate PRs, duplicate migrations, duplicate notifications
If a retry can cause a duplicate side effect, the operation needs an idempotency key. This is application code, not a model instruction.
03

Bounded retries

Every retry loop needs a maximum count and a failure escalation path. Unbounded retries waste resources, can amplify failures, and mask underlying problems.

Retry strategies: immediate, fixed backoff, exponential backoff - choose based on whether the failure is likely transient or persistent. Transient failures (network blips, rate limits) benefit from backoff. Persistent failures (wrong approach, missing capability) should fail fast.

When retries are exhausted: fail explicitly, preserve state, escalate to the orchestrator or a human. Silent retry exhaustion is a bug.

Concrete Artemis connection

  • Retries are bounded at the workflow level with a maximum count
  • When exhausted, the workflow enters a failed state with full context preserved
  • The failure state captures what was attempted, what evidence was gathered, and why it failed
  • This enables either human review or automated escalation
An unbounded retry loop is not resilience. It is a system that can waste unlimited resources while hiding a problem it cannot solve.
04

Crash recovery

The system should resume from where it left off, not start over. This requires persisted state at each transition, idempotent operations, and a recovery path from each state.

What to persist

  • Workflow state at each transition
  • Completed operation keys (for idempotency checks)
  • Intermediate results
  • Evidence gathered so far

What not to persist

  • Model conversation history - regenerate from state
  • Temporary working memory - reconstruct from context

The distinction matters. Persisting conversation history creates brittle coupling to a specific model interaction. Persisting workflow state creates durable recovery points.

Concrete Artemis connection

  • Workflow state is persisted at each transition
  • On restart, the system loads the last persisted state and resumes from that point
  • Idempotent tool calls ensure any operations at the crash boundary are safely re-attempted
  • The system knows exactly where it was and what it had already done
05

Graceful degradation

When full capability fails, provide reduced but still useful capability rather than nothing. The key requirement: be honest about it.

Degradation strategies: fall back to simpler models, reduce scope, provide partial results with clear limitations, escalate to humans. Each strategy should be designed upfront, not improvised during an outage.

The user or downstream system should know when degradation is happening. Silent degradation is a lie - it produces output that looks normal but is actually wrong or incomplete.

Concrete Artemis connection

  • When investigation reaches its limits, the system can delegate to a specialist agent
  • It can escalate for human review via approval gates
  • It can provide a partial investigation summary with explicit gaps
  • The workflow state captures what was attempted and where the limitation was hit
Silent degradation produces output that looks normal but is wrong. Honest degradation lets consumers adjust their trust and take appropriate action.
06

Turning failures into improvements

Individual failure: fix it. Systemic failure: change the architecture. The distinction matters because the fix should match the failure category.

Capture failure
       ↓
Understand the failure mode
       ↓
Add to eval dataset
       ↓
Change system
       ↓
Run evals
       ↓
Prevent regression

Categories of fix

  • Prompt/context change - cheap, fast, suits wording and emphasis issues
  • New rule or validation - medium cost, suits boundary issues
  • Tool boundary change - medium cost, suits capability scope issues
  • Architectural change - expensive, durable, suits structural problems

Match the fix to the failure category. Don't use a prompt change for a structural problem or an architectural change for a wording issue.

Concrete Artemis connection

When the investigation loop struggled with a real production issue, the fix wasn't a better prompt. It was an architectural change - separating the durable workflow from disposable specialist agents. The failure became a design insight.

A prompt change fixes a case. An architectural change fixes a category. Know which one you need.
INTERVIEW SHORTCUT

Interview distinction

Idempotency

Safe to retry
Same result whether executed once or many times. Keyed by workflow context.

Bounded retries

Fail explicitly
Maximum count, escalation path, no infinite loops.

Crash recovery

Resume, don't restart
Persisted state, idempotent operations, recovery from any state.

Graceful degradation

Useful even when broken
Reduced capability with honest limitations, not silent failure.

The mark of a mature AI system is not that it never fails. It is that failure is bounded, recoverable, and educational.
