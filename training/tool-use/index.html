Tool use & structured outputs

Designing tool interfaces the model can use reliably, structured generation that applications can consume, and the validation boundaries between probabilistic outputs and deterministic systems.

01

Why tool use matters

Tool use is how models take actions in the real world - the bridge between reasoning and consequences. Without tools, a model can only produce text. With tools, it can query databases, call APIs, modify files and trigger workflows.

The model proposes, the application disposes. Tool calls are requests, not commands. The model generates a structured request to call a tool. The application decides whether to honour that request, validates the parameters, executes the tool, and returns the result.

Tool design quality directly affects model reliability. Unclear interfaces produce unreliable calls. If the model can't tell what a tool does, what parameters it needs, or what it returns, it will guess - and guessing means errors.

Artemis connection: the model proposes tool calls, the application checks state and policy, executes the tool, records the result, then independently verifies before the workflow advances. The model never has direct authority over consequential actions.
02

Designing tool interfaces

Good tool interfaces have a clear name, typed parameters, and explicit descriptions of what each parameter does and what the tool returns. The model reads these descriptions as part of its context - they are effectively prompt content.

Fewer, focused tools beat many overlapping tools. A smaller action space means the model is less likely to pick the wrong tool or confuse similar tools. Each tool's purpose is clearer when it doesn't overlap with three others.

Tool descriptions are part of the prompt - they consume tokens and affect model behaviour. Verbose or ambiguous descriptions degrade performance. Treat them as carefully as any other prompt text.

Error responses should be informative enough for the model to adjust, not just "failed". A good error tells the model what went wrong and what it can try instead.

Artemis connection: available tools are scoped to the current workflow state. The model only sees tools valid for the current step, reducing invalid calls and keeping the action space focused.
03

Structured outputs

JSON mode and structured output mode constrain the model to produce valid structure. The API guarantees that the output matches a given schema - valid JSON, correct types, required fields present.

Schema design matters: clear field names, explicit types, enums for constrained choices. A well-designed schema communicates intent the same way a good type system does.

Structured outputs guarantee valid structure, not valid content. The model can produce a perfectly formatted JSON object that is completely wrong.

The structure is guaranteed by the API, but the content is still probabilistic. A valid JSON object can contain wrong information, nonsensical values, or hallucinated references. Structural validity is necessary but not sufficient.

Use structured outputs when downstream code needs to parse the result. Use freeform text when the output is for humans. This is a pragmatic boundary, not a quality judgement.

Artemis connection: tool call arguments are structured. Investigation summaries and evidence are structured data, not freeform strings the application has to parse. This lets the application programmatically check completeness and extract key fields.
04

Validation boundaries

The boundary between model output and application action is where validation lives. This is the most important architectural seam in any tool-using system.

Three layers of validation

  • Validate structure - is this valid JSON, do required fields exist, are types correct? Usually handled by structured output mode.
  • Validate semantics - is this a valid state transition, does this tool exist, are parameters in range? This is application responsibility.
  • Validate consequences - should this action be allowed given current state and policy? This is guardrail territory.
Artemis connection: the application checks state and policy before executing a tool call. The model cannot bypass state machine rules by generating a creative tool call. A request for an action not permitted in the current state is rejected with an informative error, regardless of how the model framed it.
05

Function calling patterns

  • Single tool call: model calls one tool, gets result, reasons about next step. The simplest pattern and often sufficient.
  • Parallel tool calls: model requests multiple independent operations simultaneously. Useful when operations don't depend on each other.
  • Sequential chains: output of one tool feeds into the next. The model orchestrates the sequence, deciding what to call based on previous results.
  • Forced tool use: require the model to call a specific tool rather than responding with text. Use it when a workflow step must produce structured output or take a specific action.

The application decides which pattern is available, not the model. This is a design decision about how much autonomy the model has at each step.

Artemis connection: workflow steps define which tools are available and whether the model can chain calls or must stop for verification. The application controls the pattern, not the model.
INTERVIEW SHORTCUT

Interview distinction

Tool interface

How does the model interact with the world?
Clear contracts, scoped availability, informative errors.

Structured output

How does the model produce parseable results?
Schema-constrained generation, valid structure with probabilistic content.

Validation boundary

Where does the application enforce rules?
Between model output and action execution - structure, semantics, and consequences.
