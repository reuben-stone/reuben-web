MENTAL MODEL

The reliability stack

Prompt → Rules → Tests → Evals → Guardrails → Feedback loop

These mechanisms overlap, but they solve different reliability problems. The interview goal is not simply to define them. It is to explain how they show up in a real system you have built.

Core Artemis principle: deterministic shell, probabilistic core. Use models where ambiguity and reasoning are valuable. Use ordinary software for state, approvals, deduplication, recovery, consequential boundaries and verification evidence.
01

Prompts

A prompt gives the model its task, context and constraints. In an agentic system, the deeper engineering question is not just how the instruction is worded, but what evidence and state should enter the context at this step?

Artemis moved away from the implicit pattern of “here is everything we know; figure it out” toward bounded, structured context: workflow objective, repository evidence, previous tool results, current state, available tools and constraints.

Concrete Artemis connection

  • ContextPacket makes context selection explicit.
  • A token budget makes context a finite engineering resource.
  • Repository and tool evidence are selected for the current task rather than blindly accumulated.
“I've become less interested in endlessly tweaking prompt wording and more interested in controlling what evidence and state the model actually receives. In Artemis, context selection is part of the architecture.”
02

Rules

Prompts describe what we want the model to do. Rules define what the surrounding application will actually permit.

  • Explicit workflow states and allowed transitions
  • Defined tool boundaries
  • Bounded retries
  • Idempotent consequential operations
  • Approval boundaries where required
  • Investigation and verification as distinct stages
  • A coding agent cannot make its own claim of success become system truth

Prompt

“Please don't perform X unless these conditions are met.”

Rule in code

“The system cannot perform X from this state.”

If something must be dependable, prefer enforcing it in software over asking the model to remember it.
03

Tests

Tests cover deterministic software behaviour. Artemis contains plenty of AI, but that does not mean every reliability question is an AI-evaluation problem.

RUNNING → WAITING_FOR_APPROVAL → EXECUTING → VERIFYING

You can test whether invalid state transitions are rejected without asking a model. The same applies to persistence, context selection, retry behaviour and idempotency.

workflowId:stepId:toolName

That idempotency key can be tested to ensure a retry does not accidentally execute the same consequential tool twice.

“Don't use an AI eval to test something ordinary software testing can establish deterministically.”
04

Evals

Evals ask whether probabilistic AI behaviour is actually performing the behaviour we care about. A useful basic shape is:

Representative dataset → System run → Scoring criteria → Result → Regression comparison

For a set of real or representative Artemis production issues, useful evaluation questions might include:

  • Did it identify the relevant repository?
  • Did it gather useful evidence?
  • Did it choose an appropriate next action?
  • Did it correctly decide whether to delegate?
  • Did it avoid claiming success without evidence?
  • Did it produce a useful investigation summary?

Real dogfooding failures are valuable because they can become regression cases. A production investigation that exposes the limits of your system's investigation loop is not merely a bug story; it is the seed of an eval case.

Important: unlike many unit tests, an eval may not have one exact expected string. It needs an explicit definition of what “good” means and a repeatable way to measure it.
05

Guardrails

Guardrails control the consequences of model failure. The strongest ones live outside the model rather than relying on a prompt saying “be careful.”

Model proposes action
        ↓
Application checks state / policy
        ↓
Tool executes
        ↓
Result is recorded
        ↓
Independent verification
        ↓
Workflow advances

Artemis examples include bounded retries, idempotency, approval gates, restricted tool boundaries, draft PRs as a human-review boundary and independent verification before a workflow can advance.

“Guardrails should limit the consequences of model failure, not merely reduce the probability that the model makes a mistake.”
06

Closing the loop on mistakes

A weak AI-development loop fixes individual failures. A stronger system turns failures into durable evidence and prevents regression.

Production failure
       ↓
Capture the case
       ↓
Understand the failure mode
       ↓
Add it to the evaluation dataset
       ↓
Change prompt / context / rule / tool / architecture
       ↓
Run eval suite
       ↓
Measure improvement
       ↓
Prevent regression

Artemis already gives you a strong example. When its investigation of a real production issue struggled, the answer was not simply a larger prompt. The realisation was that the system was gradually rebuilding a coding agent, and the correct response was to change the architectural boundary.

Artemis now owns the durable workflow, context, delegation and independent verification. A specialist coding agent can own repository-level investigation and execution, then disappear. The surrounding system cannot.

Closing the loop can produce a prompt change, but sometimes the correct result is a rule, a new eval, a tool boundary or an architectural change.
INTERVIEW SHORTCUT

Tests vs evals vs guardrails

Tests

Did the software behave correctly?
Deterministic application behaviour.

Evals

Did the AI behaviour perform well enough?
Probabilistic behaviour against representative cases.

Guardrails

What happens when the AI is wrong?
Bound authority and consequences.

Feedback loop

How does a failure improve the system?
Capture, evaluate, change and prevent regression.

The model can reason. The application still owns truth, state, authority and evidence.
