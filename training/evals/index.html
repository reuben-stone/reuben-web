01

What evals actually measure

Evals measure whether probabilistic AI behaviour performs well enough, not whether it is "correct." A unit test has a right answer. An eval needs an explicit definition of what "good" means for this specific behaviour, and a repeatable way to measure it.

The key question is always: what does "good" mean for this specific behaviour? That question is harder than it sounds, because "good" changes depending on the task, the stakes, and the user.

Artemis connection

  • Did the system identify the right repository?
  • Did it gather useful evidence?
  • Did it choose an appropriate next action?
  • Did it avoid false success claims?
Before you can evaluate anything, you have to decide what "good" means clearly enough that you can measure it.
02

Representative datasets

An eval dataset must cover the distribution of real usage, not just happy paths. If your dataset only contains cases the system handles well, your eval suite is measuring self-congratulation, not quality.

Sources for good eval cases: production logs, dogfooding failures, edge cases, and deliberately adversarial examples. The best cases are real failures that exposed genuine system limitations.

Small, curated datasets beat large noisy ones for focused evaluation. You want each case to test something specific, not a thousand cases that all test the same behaviour.

Artemis connection

Real production failures - like investigation loops that struggled to converge on a diagnosis - become regression cases. A production issue that exposed the limits of the system's reasoning is not just a bug story. It is the seed of an eval case.

Dataset principle: quality and coverage matter more than volume. Start with 20-50 focused cases that cover the important behavioural modes. Grow by adding production failures, not by generating synthetic data.
03

Scoring approaches

Deterministic graders

Pattern matching, field extraction, boolean checks. Use when correctness is programmatically verifiable. Did it pick repository X? Does the output contain field Y? Is the format valid JSON?

Model-as-judge

Use when output quality is subjective or the output space is too large to enumerate. A model evaluates the output against criteria you define. Requires its own calibration - the judge model has biases too.

Rubric-based scoring

Define dimensions (relevance, completeness, safety) with explicit levels for each. More structured than binary pass/fail, more reproducible than vibes. Calibrate by measuring agreement between the rubric and human judgement.

Human evaluation

The gold standard but expensive. Use for calibrating automated approaches, for high-stakes decisions, and when you suspect your automated scoring has drifted from real quality standards.

Artemis connection

"Did it pick the right repository" is deterministic - a grader can check that. "Did it produce a useful investigation summary" needs a rubric or model-as-judge, because usefulness is not a boolean.

Match your scoring approach to the nature of the output. Deterministic checks for verifiable facts. Rubrics or model-as-judge for qualitative judgement.
04

Offline vs online evaluation

Offline

Fixed dataset, pre-deployment
Regression checking, repeatable scoring, controlled comparison across prompt iterations.

Online

Live system, post-deployment
Production output sampling, user feedback signals, distribution shift detection.

Both are necessary. Offline evals catch regressions before they reach users. Online monitoring catches when real production usage drifts from the eval dataset - which it always eventually does.

Artemis connection

Offline evals catch prompt and context regressions before deploy. Online monitoring catches when real production issues drift from the eval dataset - new issue types, new repositories, new failure modes that the offline suite hasn't seen yet.

Key insight: if your offline evals pass but users report degraded quality, your eval dataset probably doesn't represent current usage. Online monitoring is how you detect that gap.
05

Regression prevention

Every production failure should become an eval case. An eval suite that only grows is fine - the cost is compute time, not engineering time. The alternative is fixing the same class of failure twice.

Version your eval datasets alongside your prompts. A prompt change can improve one behaviour while regressing another. Without versioned datasets you cannot reproduce or compare results across prompt iterations.

Production failure
       ↓
Capture input state + system behaviour
       ↓
Define correct behaviour
       ↓
Add to regression suite
       ↓
Run after every prompt / context change
       ↓
Prevent recurrence

Artemis connection

Closing the feedback loop means failures become durable regression tests, not just one-off fixes. When an investigation loop struggles, the captured case prevents future prompt or context changes from reintroducing that failure mode.

The goal is not a perfect eval suite. The goal is a suite where production failures stop being novel and start being regressions you already catch.
INTERVIEW DISTINCTION

Choosing the right evaluation approach

Deterministic grader

Can a program check this?
Use for field extraction, format checks, factual lookups.

Model-as-judge

Is this qualitatively good?
Use for summaries, reasoning quality, open-ended outputs.

Rubric scoring

What dimensions matter?
Define explicit levels per dimension, calibrate with human agreement.

Regression suite

Did we break what worked?
Run on every change, grow from production failures.

The hardest part of evals is not building the framework. It is defining what "good" means clearly enough that you can measure it.
