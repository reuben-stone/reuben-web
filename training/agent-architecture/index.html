01

What is an agent, architecturally?

An agent is a model in a loop: observe state, reason, act, observe result, repeat.

The interesting engineering is not the loop itself but the boundaries: what can the agent observe, what actions are available, when does it stop, who verifies its work.

Most "agent" failures are boundary failures - the agent had too much authority, too little information, or no verification.

Artemis connection: Artemis wraps the agent loop in a durable workflow with explicit states, bounded tools, and independent verification. The agent reasons; the application enforces.
02

State machines for workflow orchestration

Explicit states and transitions make workflows debuggable, recoverable, and auditable.

Each state defines: what information is available, what actions are permitted, what transitions are valid.

Invalid transitions are rejected by the application, not negotiated with the model.

State machines make it possible to resume after crashes - you know exactly where to pick up.

Artemis connection: RUNNING → WAITING_FOR_APPROVAL → EXECUTING → VERIFYING. Each state has defined tool boundaries and transition rules enforced in code.
03

Delegation patterns

Single agent: one model handles everything. Simple but fragile for complex tasks.

Orchestrator + specialists: a coordinator delegates subtasks to focused agents with scoped contexts.

The key decision: what does each agent own, and what goes back to the orchestrator?

Specialist agents should be stateless and disposable - do the task, return results, disappear.

The orchestrator owns the durable workflow. Specialists own temporary execution.

Artemis connection: Artemis owns the durable workflow, context, delegation and independent verification. A specialist coding agent owns repository-level investigation and execution, then disappears. The surrounding system cannot disappear.
04

Durable execution

Workflows that survive crashes, restarts, and partial failures.

State is persisted at each transition, not just held in memory.

Idempotent operations prevent duplicate side effects on retry.

Bounded retries prevent infinite loops - fail explicitly rather than silently retrying.

Artemis connection: Workflow state is durable. Each tool execution is idempotent (workflowId:stepId:toolName keys). Retries are bounded. The system can crash and resume from the last persisted state.
05

When agents vs deterministic code

Use agents where ambiguity and reasoning add value: investigation, evidence gathering, synthesis, decision-making under uncertainty.

Use deterministic code where correctness matters: state management, approval flows, deduplication, verification evidence, consequential boundaries.

The mistake is using an agent for everything or using deterministic code for everything.

Artemis connection: This is "deterministic shell, probabilistic core" applied to architecture. The model investigates and reasons. The application manages state, enforces rules, and verifies outcomes.
